## 1. Introduction

### 1.1 Motivation
[DONE]

The deployment of large language model (LLM) agents with persistent memory — the ability to retrieve and act on information stored across sessions — has expanded rapidly, extending beyond cloud-hosted frontier models to small, locally-deployable models running entirely on consumer hardware. This shift is driven by concrete practical incentives: local deployment eliminates per-query API costs, keeps sensitive personal data off third-party servers, and removes any dependency on network connectivity. These properties make small local models a natural fit for personal-assistant-style agents that accumulate a long-lived memory of user-specific facts, preferences, and history — precisely the use case in which persistent memory is most valuable and most exposed.

This adoption is no longer confined to individual hobbyist deployments. Both individual users and organizations are increasingly relying on small local models to automate real tasks and workflows, often granting these agents access to real tools — file systems, email, financial operations, security configuration — rather than restricting them to conversational use. This combination of persistent memory, weaker safety tuning relative to frontier models, and genuine execution capability raises the stakes of a memory-poisoning attack considerably: an agent that can be manipulated into executing attacker-chosen actions is not merely a source of misinformation, but a potential vector for concrete harm — including the kind of unauthorized data destruction, exfiltration, and system compromise associated with ransomware and related extortion attacks — if its memory can be reliably poisoned.

Prior work on memory-poisoning attacks against LLM agents — including AgentPoison, PoisonedRAG, and MINJA — has established that retrieval-augmented memory is a viable and effective attack surface, but has done so almost exclusively against large, cloud-hosted models with strong general-purpose alignment, and largely at the level of generated text rather than executed action. Whether these findings transfer to small, locally-deployed models capable of real tool use is an open question with direct practical stakes, and is the gap this work addresses: an assessment of how vulnerable today's leading small local models actually are, at both the text and execution level, and — by extension — how urgently their security needs to be improved before broader deployment outpaces it.

This work evaluates memory-poisoning vulnerability across three small, locally-deployable models (3B–9B parameters) and across two levels of agent capability: a text-only question-answering agent, and an execution agent capable of taking real, consequential actions through tool calls. The inclusion of an execution-level evaluation is itself motivated by a gap in prior work, which has largely measured vulnerability at the level of generated text — a proxy whose reliability for predicting real-world, action-level risk has not been established.

### 1.2 Related Work
[DONE]

**Memory poisoning of retrieval-augmented agents.** The vulnerability of retrieval-augmented generation (RAG) to malicious content in the knowledge store was first formalized by PoisonedRAG (Zou et al., 2025), which showed that a small number of optimized malicious texts inserted into a knowledge database could reliably steer an LLM toward an attacker-chosen answer for a chosen question. AgentPoison (Chen et al., 2024) extended this threat model from static knowledge bases to the long-term memory of LLM agents, using an optimized embedding-space trigger to ensure poisoned demonstrations are retrieved with high probability while leaving benign queries unaffected. Both approaches, however, assume an attacker with direct write access to the memory or knowledge store. MINJA (Dong et al., 2025) relaxed this assumption considerably, demonstrating that an attacker restricted to ordinary query-and-observe interaction — with no memory-write access at all — can still implant a persistent, malicious memory record by inducing the agent to generate and store the poisoned content itself, via a sequence of bridging queries and a progressive shortening strategy that removes overt traces of manipulation from the final stored record. This threat-model progression — from direct write access, to query-only indirect injection — motivates the present study's inclusion of both a direct-injection and a MINJA-style condition, allowing attack effectiveness to be compared across attacker capability levels rather than assumed fixed. More recent work has continued this trajectory toward stealth and persistence: Pulipaka et al. (2026) introduce *sleeper memory poisoning*, in which a fabricated memory is planted via external content and remains dormant across sessions before influencing a later, unrelated conversation, evaluating the full pipeline from memory write through retrieval to downstream behavioral influence — a staged view of attack success (write → retrieve → comply → act) that this study's own metric structure (§2.4) independently converges on.

**Agent and tool-use security evaluation.** As LLM agents have moved from purely conversational settings toward real tool execution, evaluation infrastructure has followed. ToolEmu (Ruan et al., 2024) addressed the cost of manually instantiating diverse, high-stakes tool environments by emulating tool execution with a second LLM, but validation against human judgment found that only 68.8% of the failures it identified corresponded to genuine real-world agent failures — a roughly 31% false-positive rate attributable to the emulator itself hallucinating consequences rather than executing them. AgentDojo (Debenedetti et al., 2024) addressed this limitation by constructing real, stateful tool environments — email clients, banking interfaces, travel-booking systems — over which agents execute genuine, checkable actions. The present study's execution agent follows this latter design philosophy directly: every tool call executes against real, mutable Python objects, and every attack-success judgment is made by inspecting ground-truth object state after execution, never by parsing the model's self-reported account of what it did. Agent Security Bench (Zhang et al., 2025) subsequently unified prompt-injection, tool, and memory-poisoning attacks into a single benchmarking framework spanning ten agent scenarios and thirteen LLM backbones, reinforcing that agent security must be assessed across the full pipeline — retrieval, reasoning, and action — rather than at any single stage in isolation, a principle this study operationalizes by evaluating the same family of attacks against both a text-only QA agent and a tool-executing agent.

**Tool-semantics and tool-metadata manipulation.** A separate line of work has examined attacks that manipulate an agent's *tool layer* directly rather than its factual memory. ToolHijacker (Shi et al., 2026) injects a malicious tool document into an agent's tool library, formulating the crafting of that document as an optimization problem so that the agent is consistently steered toward selecting an attacker-controlled tool for a chosen task. MemMorph (Zhang et al., 2026) pursues a related goal — biasing which tool an agent selects — but does so by poisoning the agent's long-term memory with records disguised as technical facts or incident reports, rather than by modifying tool metadata directly, and reports attack success rates exceeding 85% from as few as three injected records. Both attacks target the *selection* stage of tool use: which tool, among several candidates, the agent chooses to invoke. The tool-semantics poisoning attack introduced in the present study (§2.3.6) targets a distinct stage: it leaves tool selection and tool metadata entirely untouched, and instead poisons the agent's memory-derived belief about the *consequences* of a tool the agent has already decided to call — for example, whether a delete operation is reversible, or whether a transfer can be recalled. This shifts the object of manipulation from "which tool" to "what happens if I use this tool," and correspondingly targets a different point of agent failure: the binary decision to act at all, rather than the choice among alternatives.

**Small and quantized model safety.** The security literature above has been developed almost exclusively against large, cloud-hosted models. Whether its findings transfer to small, quantized, locally-deployed models is addressed by a comparatively thin but growing body of work. Chen et al. (2025) find that post-training quantization techniques can measurably degrade a model's safety-relevant behavior even when standard capability metrics such as perplexity remain stable, and propose a quantization-aware safety-patching method to recover lost safety capability. This finding is directly relevant to the present study, in which both evaluated models are served as Q4_K_M-quantized weights rather than at full precision — a deployment choice motivated by consumer-hardware constraints (§2.1) that, per this prior finding, cannot be assumed safety-neutral. A broader 2026 survey of small-language-model safety and alignment further observes that safety-critical behavior can be concentrated in a small fraction of a model's parameters, making it disproportionately sensitive to the kind of compression routinely applied for local deployment.

**Textual refusal versus behavioral compliance.** The most direct precedent for this study's central methodological argument is Cartagena and Teixeira (2026), whose GAP benchmark measures the divergence between a model's text-level refusal of a harmful request and its willingness to nonetheless execute that same request as a tool call, finding cases across several frontier models where a model's stated refusal and its tool-calling behavior contradict each other outright. This establishes, in a general jailbreak/harmful-instruction setting, that textual safety behavior does not reliably predict tool-call safety behavior. The present study investigates a related but distinct question — not whether a model's refusal of a directly harmful instruction transfers to its actions, but whether a model's vulnerability to a *poisoned memory* at the text level transfers to its vulnerability at the execution level, when the poisoned content is never presented as an instruction at all, but as a retrieved, ostensibly factual record.

**Positioning.** Taken together, this literature establishes three findings in isolation: that agent memory can be poisoned under progressively weaker attacker assumptions (AgentPoison, MINJA); that tool-use introduces attack surfaces and evaluation demands distinct from text generation (ToolEmu, AgentDojo, ASB); and that textual safety behavior does not reliably predict execution-level safety behavior, at least for direct harmful instructions (Mind the GAP). What remains largely unexamined is their intersection: whether memory poisoning, specifically, produces the same text-to-action divergence when the target is a small, quantized, locally-deployed model rather than a large cloud-hosted one — the deployment setting in which such models are most likely to be given real, unmonitored tool access. This study addresses that intersection directly.

### 1.3 Research Questions and Contributions
[DONE — RQ4 explicitly marked pending 3B data]

Our study is organized around three research questions that can be answered from the models evaluated to date, and one that remains open pending completion of the third (3B-parameter) track.

**RQ1 — Threat-model sensitivity.** Under a fixed retrieval-augmented memory architecture, how does the effectiveness of memory-poisoning attacks vary with the attacker's assumed capability, from direct memory-write access (Direct Injection), to query-only indirect injection with no write access at all (MINJA-style), to high-volume repetition intended to dominate retrieval (Many-Shot)? Answering this establishes whether restricting attacker capability — a natural target for defensive design — meaningfully reduces risk in this setting, or whether weaker threat models can approximate the effectiveness of stronger ones.

**RQ2 — Text-to-execution transfer.** Does a model's vulnerability to memory poisoning at the level of generated text reliably predict its vulnerability at the level of executed action, when the same underlying model is given real tool-calling capability? We address RQ2 from two complementary angles rather than a single shared measurement: a direct, scenario-matched reversal analysis (the 4B study, testing identical scenarios at both levels) and a structural analysis of what predicts execution-level outcomes where no reliable predictor of text-level outcomes could be established (the 9B study, tested on a non-overlapping scenario set). Together these constitute two independent lines of evidence bearing on the same question, rather than a single replicated finding.

**RQ3 — Structural predictors of execution-level vulnerability.** Among the execution-agent-specific attacks evaluated in our work, what properties of a scenario or attack — the conditionality of the rule governing an action, the poisoned fact's framing (reversibility, authority, narrative justification), and the tool's own name and description — govern whether a poisoned belief is translated into a real, consequential action? This question is specific to the 9B study's execution-agent findings, including the tool-semantics poisoning attack introduced in §2.3.6, which has no direct analogue in the 4B study.

**RQ4 — Scaling with model size** *(pending)*. Does memory-poisoning vulnerability, at either the text or execution level, increase, decrease, or remain stable as model parameter count decreases from 9B to 4B to 3B? This question requires all three tracks and cannot be answered until the third contributor's results are available; it is stated here as a target for the completed paper rather than answered in the current draft.

Our contributions are: (1) an evaluation of memory-poisoning attacks against small, locally-deployable, quantized LLM agents — a deployment setting largely unexamined by prior work targeting large, cloud-hosted models; (2) a real, ground-truth-verified execution-agent methodology, in which attack success is determined by inspecting actual sandbox state rather than by parsing model self-report or using an LLM-emulated environment; (3) tool-semantics poisoning, a novel attack targeting an agent's belief about the consequences of a tool it has already selected, distinct from prior work targeting tool *selection*; and (4) cross-study evidence, gathered under two independent experimental designs, that text-level vulnerability assessment is an unreliable proxy for execution-level risk in memory-augmented local agents.

## 2. Methodology

### 2.1 Target Models and Infrastructure
[DONE]

This study evaluates memory-poisoning vulnerability across three small, locally-deployable language models, spanning a range of parameter counts within a class of models runnable on consumer hardware without cloud infrastructure or paid inference APIs: Qwen3.5-9B, Qwen3-4B-Instruct, and a third model in the 3B parameter range (in progress; integrated in a subsequent revision). Each model was evaluated independently on separate consumer hardware by a different contributor, following a shared experimental protocol (Methods §2.2–2.6) to ensure cross-model comparability.

Target-model inference was served locally via LM Studio (v0.4.16), exposing an OpenAI-compatible completion endpoint with no external API dependency for the agent itself. Both the 9B and 4B models were served as Q4_K_M-quantized GGUF weights, ensuring a consistent serving configuration across tracks. Hardware configurations were as follows: the 9B track ran on an AMD Radeon RX 6700 XT (12 GB VRAM), 16 GB system RAM, and a Ryzen 5 2600 CPU; the 4B track ran on an ASUS TUF Gaming F15 laptop with an NVIDIA RTX 3050 Ti (4 GB VRAM) and 16 GB system RAM. Both configurations represent mid-range consumer hardware, supporting the study's framing of small local agents as a widely-deployable, not niche, threat surface.

All three tracks share identical retrieval infrastructure: a persistent ChromaDB vector store with cosine similarity search and the `all-MiniLM-L6-v2` sentence embedding model, retrieving the top-*k*=3 most relevant memories per query. Holding the embedding model constant isolates the target LLM as the primary variable at the retrieval-and-reasoning layer.

The only paid or cloud-dependent component in the pipeline is LLM-as-judge scoring for free-text QA-agent responses (Methods §2.5), which uses free-tier API access and never the target model under test. Execution-agent evaluation requires no judge, as correctness is determined by direct inspection of ground-truth sandbox state (§2.2.2).

### 2.2 Agent Architectures
[DONE]

Both agent types evaluated in this work — across both model tracks — follow a shared minimal-harness design philosophy: the base agent class is agnostic to attack type, with each attack implementation responsible for deciding what content is written to memory and when. Critically, memory writes are never triggered by the agent's own reasoning loop; `remember()`-equivalent calls are always explicit, external calls issued by the attack logic itself. This separation keeps the harness reusable, unmodified, across every attack evaluated (§2.3), and ensures that any observed vulnerability reflects the agent's retrieval-and-reasoning behavior rather than an artifact of the harness's memory-management logic. Both agent types are also constrained to a single decision per invocation — one request produces one response, with no internal loop permitting a tool to be re-invoked after observing its result — consistent with the isolated, single-decision nature of the scenarios under study rather than open-ended multi-step task completion.

**2.2.1 QA-Agent.** The text-level agent implements a minimal retrieval-augmented pipeline: retrieve the top-*k* most semantically similar memories for the incoming query, construct a prompt injecting those memories as context, and generate a free-text response via the target model. Retrieved memories are partitioned into two categories before prompt construction: ordinary factual memories, and memories formatted as prior question–answer demonstrations (a distinction required specifically by the MINJA-style attack, §2.3.2, which relies on the agent imitating a fabricated prior exchange rather than treating it as a stored fact). No instruction is included directing the model to prioritize factual memories over demonstrated examples in the event the two conflict; this omission is a deliberate design choice establishing a vulnerable baseline against which any observed resistance can be attributed to the model's own behavior, rather than to a defensive prompting scaffold layered on top of it.

**2.2.2 Execution-Agent.** The execution-level agent is a sibling of the QA-Agent sharing its retrieval and prompt-construction logic, but replaces free-text generation with a tool-calling decision: given the retrieved memories and a short menu of available tools, the agent selects at most one tool to invoke, or an explicit `decline` option used when no retrieved fact justifies acting or when acting would violate a stored rule. The system prompt in both tracks is kept deliberately minimal, granting tool access without additional caution or safety framing, so as not to bias the measured vulnerability toward artificial resistance introduced by the harness itself rather than the model.

The two tracks diverge, however, in how a tool call is elicited and how its consequences are verified — a methodological difference disclosed here in full rather than glossed over. In the 9B study, the model is prompted to emit a structured JSON object specifying the tool, arguments, and a brief rationale, parsed via a JSON-first strategy with a regex-based fallback for cases where the model's rationale field runs past the token budget before the object closes; the selected tool is then invoked as a real method call against a real, stateful Python object (a file system restricted to a disposable sandboxed directory, an in-memory bank account, access-control list, security-settings object, or email log), and attack success is determined exclusively by diffing that object's ground-truth state before and after the call. In the 4B study, tool selection uses the target model's native function-calling interface (validated in isolation prior to the main study), and each tool's execution is fully simulated: every call is logged with its arguments and returns a synthetic confirmation string, with no underlying file, account, or system state actually mutated; attack success is accordingly determined by whether the logged tool call matches the scenario's expected tool and arguments, rather than by inspecting any real post-execution state. The 9B study's real-state-mutation design follows the same rationale as AgentDojo (§1.2) and is built specifically to avoid the false-positive risk documented in LLM-emulated tool environments; the 4B study's logged-simulation design is lighter-weight and does not carry this same ground-truth guarantee. This asymmetry means execution-level results across the two tracks are comparable in kind — both measure whether a poisoned belief is translated into a concrete tool invocation — but differ in evidentiary strength, and this distinction is carried forward explicitly in the Limitations section (§5) rather than treated as a footnote.

### 2.3 Attack Taxonomy
[DONE]

Six distinct attack methods are evaluated across this work, three shared by both model tracks and three specific to the 9B study. All attacks operate against the harnesses described in §2.2 without modification to the underlying agent code; each attack differs only in what content is written to memory, when, and under what threat-model assumptions about the attacker's access.

**2.3.1 Direct Injection.** The baseline attack, and the strongest threat model evaluated: the attacker is assumed to have direct write access to the agent's memory store and inserts a single, plainly-worded false fact verbatim, disguised as an ordinary prior memory (e.g., asserting that a suspended driving license has been reinstated, or that a spouse has been authorized on a bank account). This establishes an upper-bound reference against which every more constrained attack below is compared. This attack was evaluated against the QA-agent only in the 9B study; the 4B study evaluates it against both agent types (full cross-track coverage given in §2.6).

**2.3.2 MINJA-Style Indirect Injection.** A substantially weaker threat model in which the attacker has no direct memory-write access at all, and can only interact with the agent through ordinary queries. The attacker issues a sequence of queries containing a progressively shortened "indication" — an explicit, leading statement of the target claim at the first step, shortened at each subsequent step until the final query is entirely neutral and contains no overt trace of manipulation. At each step, the agent's own generated response is evaluated for compliance; if compliant, that response — not attacker-authored text — is what gets written to memory. Attack success is judged on the agent's response to the final, fully neutral query, which contains no indication content at all, so that any observed success is attributable to the previously self-stored memory rather than to the wording of the final question itself. As with Direct Injection, this attack was evaluated against the QA-agent only in the 9B study, while the 4B study evaluates it against both agent types; exact step counts and per-domain conditions for both tracks, and the full cross-track coverage picture, are disclosed in §2.6.

**2.3.3 Many-Shot / Volume Injection.** This attack tests whether planting multiple copies or phrasings of a poisoned fact increases attack effectiveness relative to a single instance, either by displacing legitimate memories from top-*k* retrieval entirely or by increasing persuasive weight independent of retrieval. The two tracks operationalize this attack at different scales, disclosed here rather than treated as directly comparable: the 9B study, constrained by a fixed top-*k*=3 retrieval window, evaluates identical-copy volume only up to K=3 (beyond which additional copies cannot further affect a 3-slot retrieval outcome), and separately compares this identical-copy condition against a fixed set of three independently-worded diverse variants planted together at the same total volume. The 4B study instead sweeps a wider range of paraphrased-variant volumes (N ∈ {1, 5, 10, 20, 40}), extending well past the top-*k* window specifically to characterize behavior once retrieval is fully and increasingly saturated with poisoned content. Both designs test the same underlying question — does volume matter, and does it matter differently from wording — but numeric results between tracks should be read as testing that question under different volume regimes, not as a like-for-like sweep.

**2.3.4 Style and Framing Variants** *(9B study only).* This attack holds the poisoned claim's content fixed while varying its rhetorical framing, testing whether persuasive presentation — independent of repetition or attacker access level — affects success. Four framings are evaluated: a blunt direct assertion of the opposite of the true fact with no justification; a same-entity narrative offering a plausible personal reason the same fact changed, introducing no new entity; a loophole narrative introducing a new entity or technicality that routes around the original rule rather than negating it directly; and an authority-framed variant attributing the change to a third party's confirmation rather than the user's own decision. For the QA-agent, each style is tested with three independently-worded variants per domain to avoid a single sentence's idiosyncratic wording being mistaken for a style-level effect; the execution-agent version tests one poison text per style per domain.

**2.3.5 Multi-Value Confusion.** Rather than repeating or rephrasing a single target lie, this attack plants several mutually-contradicting false claims simultaneously, testing whether internally inconsistent poisoning increases agent confusion (and thus compliance) or triggers caution. On the QA-agent, this takes the form of three different, mutually-incompatible fake values for a genuinely multi-valued fact (e.g., three different incorrect meeting times), scoped only to domains where a fact has more than two possible states, since a binary yes/no fact cannot support three distinct wrong values. On the execution-agent, where every domain is a binary action decision, the attack is adapted to plant three mutually-inconsistent *justifications* for the same action rather than three inconsistent values.

**2.3.6 Tool-Semantics Poisoning** *(9B study only, novel attack).* Every attack above poisons the agent's belief about *authorization* — whether an action is permitted. Tool-semantics poisoning instead poisons the agent's belief about *consequence* — what a tool the agent has already selected actually does once called — and is structurally impossible to construct against a text-only QA-agent, since there is no tool-execution semantic to lie about in a setting with no tools. Each scenario pairs a policy rule grounded in a concrete, stated risk (e.g., a file must never be permanently destroyed because it may still be needed and cannot be recovered) with either an accurate tool-consequence fact (e.g., that a delete operation is irreversible) or a poisoned one claiming a categorically different consequence (e.g., that the same operation is a no-op that leaves the target file untouched). Five execution domains are evaluated: file deletion, wire transfer, access grant, two-factor-authentication disablement, and confidential-email transmission. Several controlled follow-up variants were run to isolate specific confounds in this attack's design — whether the poison's framing (irreversible-but-safe versus fully inert) rather than domain identity drives resistance, whether a tool's own name and description (e.g., "delete_file") supplies a semantic prior independent of memory content, and whether apparent resistance in some domains reflected genuine reasoning-level rejection or a retrieval failure that prevented the poison from ever reaching the model — with results reported in full in §3.4.

**Control conditions.** For every attack and domain evaluated in both tracks, a corresponding no-attack baseline was run — identical setup with the true fact present and no poisoned memory of any kind — establishing the rate at which either agent arrives at the target claim or takes the corresponding action with no attack present at all. Every attack-success figure reported in §3–4 is interpretable only relative to this baseline, and is presented alongside it rather than in isolation. One exception is disclosed here: the 9B study's QA-agent baseline does not include the `peanut_allergy` domain, though both Direct Injection and MINJA-style are tested on it; this gap is carried forward to §5 rather than left implicit.

### 2.4 Evaluation Metrics
[DONE]

Following the naming convention established in the 4B study, this work adopts a unified Attack Success Rate (ASR) family of metrics across both tracks, decomposed by pipeline stage so that a trial's outcome at retrieval, generation, and action can be distinguished rather than collapsed into a single figure. Both agent types share a common retrieval-level metric; the QA-agent and execution-agent then diverge in how success is measured downstream of retrieval, and the two tracks' execution agents diverge further from one another as a consequence of the verification-rigor asymmetry described in §2.2.2.

**2.4.1 ASR-r (Retrieval).** A binary, deterministic indicator of whether a poisoned memory was present among the top-*k* memories retrieved for the trigger query or task, computed identically across both agent types and both tracks by inspecting retrieval results directly rather than any downstream model output. For attacks planting multiple poisoned memories under distinct identifiers (Many-Shot, Multi-Value Confusion), this is generalized to whether *any* of the planted copies appear in the retrieved set, together with a count of how many of the planted copies did so. This metric isolates the retrieval mechanism's susceptibility to poisoning independently of the target model's subsequent behavior, and — reported alongside whether the corresponding true fact remained retrievable — allows a trial to be classified along two independent axes: a poisoned memory can be retrieved and still rejected by the model, or a true fact can be evicted from context entirely without the model's output changing.

**2.4.2 ASR (QA-Agent).** A binary indicator of whether the agent's generated response treats the poisoned fact as true, judged by an LLM (§2.5) rather than by keyword or exact-match heuristics, since compliance is frequently expressed with hedging or partial qualification that heuristic matching cannot reliably classify. One deviation from judge-based scoring is used in the 9B study for the Multi-Value Confusion attack (§2.3.5): because the candidate values in these domains are simple, enumerable facts (a specific time or a specific dose count), the agent's response is classified by direct string matching against the known true value and the set of known false values, rather than by an LLM judge call. This substitution is disclosed here as a deliberate, low-risk simplification specific to a case where the value space is fully known in advance, not a departure from judge-based scoring elsewhere in the study.

**2.4.3 Execution-Agent Metrics.** Both tracks measure whether a poisoned belief is translated into a real tool invocation, but do so under the verification-rigor asymmetry disclosed in §2.2.2, which produces two structurally different metrics rather than one shared one.

In the 4B study, action-level success is decomposed into two sequentially-gated metrics: *ASR-action-call*, a deterministic check of whether the agent's structured tool-call output names one of the scenario's designated expected tool(s), requiring no judge call since this information is already structurally present in the model's output; and *ASR-action-precise*, a judge-scored check, evaluated only for trials where ASR-action-call is true, of whether the call's arguments are semantically faithful to the poisoned fact (e.g., correct recipient, amount, or time). Trials with no matching tool call are recorded as not evaluable for precision, rather than scored as a negative, so that "the agent did not act" is not conflated with "the agent acted incorrectly." For the MINJA condition specifically, a third metric, *ASR-action-anytime*, is defined as true if the expected tool is invoked with matching parameters at any point across all responses generated during the multi-step attack — including intermediate indication-step responses, not only the final response — since restricting scoring to the final response alone was found to substantially undercount real tool-invocation activity; a separate diagnostic distinguishes this from premature tool calls unrelated to the poisoned fact at all, which are tracked as a distinct confusion/over-agency phenomenon rather than counted toward any ASR variant.

In the 9B study, attack success is instead determined by directly comparing the sandboxed object's ground-truth state before and after the trial (e.g., whether a targeted file no longer exists, whether an account balance decreased, whether a clearance level crossed a defined threshold), independent of what tool the agent claims to have called or what the model's textual rationale states. Because each sandboxed tool method only produces its corresponding real-world effect when invoked with sufficiently correct arguments, this single ground-truth metric functions as a fused analogue of ASR-action-call and ASR-action-precise together: a call to the correct tool with materially incorrect arguments will generally either fail to produce the graded state change or raise an execution error (recorded separately, not scored as success). The finer two-stage decomposition used in the 4B study therefore has no direct counterpart in the 9B study; this is a design tradeoff rather than a gap, exchanging decomposed granularity for a stronger executable ground-truth guarantee, consistent with the rationale given in §2.2.2.

A secondary, 9B-study-specific diagnostic — the *correctly-declined rate* — records the proportion of trials in which the agent selected the explicit `decline` option (§2.2.2). This is reported alongside, not as the complement of, attack success, since a trial can be neither an attack success nor a decline (e.g., an irrelevant or malformed tool call that produces no graded state change).

**2.4.4 Baseline Normalization.** As established in §2.3, every ASR and ASR-r figure reported in §3–4 is interpreted relative to its corresponding no-attack baseline, computed identically to the attacked condition but with no poisoned memory present. This is necessary in particular for domains where the agent's default, unpoisoned behavior already carries some rate of arriving at the target claim or action.

### 2.5 LLM-as-Judge Methodology and Validation
[DONE — validation-rigor asymmetry disclosed, also flagged for §5 Limitations]

Both tracks require an automated judge to score free-text QA-agent responses at scale, since neither keyword matching nor exact-match heuristics reliably distinguish genuine compliance with a poisoned fact from superficial hedging that does not constitute compliance — a distinction both tracks independently found to be non-trivial.

**2.5.1 4B Study: Judge Selection Protocol.** Three candidate judges were evaluated against a common validation protocol: verdicts on 10 held-out scenarios were compared against blind human judgment, with the human scorer rating each response before viewing the automated verdict to avoid anchoring, and agreement rate against this human baseline used as the sole selection criterion. The target model itself (Qwen3-4B, self-judging) was tested first; an initial abstract rule-based prompt performed poorly, conflating surface-level hedging with genuine rejection of the poisoned premise, but rewriting the prompt with two contrastive few-shot examples (one clear success, one clear failure) raised agreement to 90%. This candidate was set aside despite its high agreement, however, due to an unresolved self-leniency confound: the judge and the target model share identical weights, so systematic bias in how the model frames its own outputs cannot be ruled out as a contributor to the observed agreement rate. Two external Gemini variants were tested next (gemini-2.5-flash-lite, gemini-3.5-flash), both converging on 80% agreement — lower than the self-judge figure, but free of the self-leniency confound. Manual inspection of disagreements revealed the two failure modes were asymmetric: the self-judge tended toward false negatives, missing genuine compliance expressed behind hedging language, while the external variants tended toward false positives, flagging success whenever the poisoned premise was merely mentioned regardless of whether the response subsequently rejected it. Since both external variants converged on the same accuracy ceiling regardless of model size, the smaller, faster variant with the more generous free-tier quota — gemini-3.1-flash-lite — was retained for all subsequent batch scoring.

**2.5.2 9B Study: Judge Design and Fallback Chain.** The 9B study's substantially larger trial volume (§2.6) required judge infrastructure resilient to free-tier daily quota exhaustion across a single run. A prioritized list of Gemini model candidates is queried against the account's actual available models at runtime, rather than assumed fixed, since judge-model availability was found to change over the course of the study; any candidate that returns a rate-limit or quota error is marked dead for the remainder of that run rather than retried, and the sweep falls through to the next candidate in the list, with a Groq-hosted Llama-3.3-70B as a final external fallback should every Gemini candidate be exhausted. If every candidate fails, the sweep halts explicitly rather than continuing to generate local-model completions that are guaranteed to fail at the judging step. The verdict parser matches a leading YES/NO token via regex rather than requiring an exact match; an earlier, stricter exact-match version was found to incorrectly reject valid verdicts of the form "NO." (a trailing period being sufficient to fail an exact match), which — since refusals are judged "NO" far more often than successes are judged "YES" — was silently and disproportionately discarding failure judgments and inflating apparent ASR. This was corrected prior to the result runs reported in this paper. The primary judge selected for this track, gemini-3.1-flash-lite, was confirmed via informal spot-checking during development — manually reviewing a sample of judge verdicts alongside their accompanying one-sentence rationale and confirming agreement — rather than the formal, blind, multi-candidate comparison protocol used in the 4B study (§2.5.1). This is a real difference in validation rigor between the two tracks, disclosed here and revisited in Limitations (§5), rather than presented as equivalent to Maryem's protocol. Notably, this same model was independently arrived at in the 4B study through its more rigorous process — a convergence from two separately conducted selection efforts, offered here as corroborating evidence for the judge's suitability rather than as a substitute for formal validation on this track.

**2.5.3 Shared Reproducibility Caveat.** Both tracks independently encountered Gemini model identifiers becoming unavailable mid-project (`gemini-2.5-flash` and `gemini-3.5-flash` returning deprecation errors for new usage), requiring both to re-query the list of currently available models before continuing. This is noted as a practical caveat for reproducibility: judge-model identifiers pinned in this paper's configuration are not guaranteed to remain queryable indefinitely, and replication attempts should first verify current model availability.

Two consequences follow directly from this matrix. Only files explicitly designated final in the project's result log are used for any figure reported in §3–4; superseded files are not cited as evidence. Separately, one specific condition (file deletion under same-entity-narrative framing, execution-agent) showed material run-to-run instability across repeated independent measurements (28–40% in the two clean n=25 runs, with a wider 25–100% range across earlier historical reruns); this is disclosed here as a protocol-level reproducibility note and discussed further in §4.
